# Support Bot УПП м. Луцьк

Внутрішній облік технічних несправностей для 100–300 працівників і 3–5 ІТ-спеціалістів. Python 3.12+, aiogram 3, PostgreSQL 16, Docker Compose v2. Розрахований на **один процес бота**.

Для розгортання **GitHub → Linux-сервер** дивіться [SERVER_DEPLOY.md](SERVER_DEPLOY.md). Docker на локальному Windows для цього не потрібен. Workflow `.github/workflows/tests.yml` підготовлений для перевірки всіх тестів із PostgreSQL на GitHub після публікації; запуск бота на сервері виконується окремо.

Поточна підготовка першого тестового запуску, блокери середовища та точний ручний контрольний список: [FIRST_TEST_RUN.md](FIRST_TEST_RUN.md). Створену `.env` не перезаписуйте шаблоном; Telegram-конфігурацію потрібно заповнити локально.

## Поведінка

- Анкета: ім'я → підрозділ → місце → категорія → опис → одне фото або «пропустити».
- Непідтверджений користувач може створити 3 заявки за рухомі 24 години. Вони мають статус `pending_verification` і **не публікуються в ІТ-групі**.
- Адміністратор підтверджує користувача: попередні заявки переходять у `new` і ставляться на доставку. Підтверджений користувач має ліміт 20 заявок за 24 години.
- «Взяти в роботу» призначає виконавця. Рядкові блокування PostgreSQL виключають одночасне призначення двох виконавців. Подальші зміни доступні виконавцю або адміністратору.
- Є історія статусів, останні 10 власних заявок, черга та статистика. Початок місяця визначається за `Europe/Kyiv`, дати зберігаються в UTC.
- Доставка карток, фото й актуального статусу повторюється автоматично; є ручний `/sync`.
- Ролі, блокування та відповідність callback повідомленню перевіряються на сервері; SQL параметризований, HTML екранується, ввід і частота дій обмежені.

## 1. VS Code і залежності

Відкрийте **папку upp_support_bot** у VS Code через File → Open Folder. Встановіть розширення Python і Pylance. Наведені команди виконуються в цій папці.

Для Docker встановіть Docker Desktop з Linux containers / WSL 2; запустіть його та перевірте:

```powershell
docker version
docker compose version
```

Для локальних тестів встановіть Python 3.12+:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Якщо launcher `py` не знаходить Python, вкажіть повний шлях до встановленого `python.exe` версії 3.12+. У VS Code: Python: Select Interpreter → `.venv\Scripts\python.exe`. Активація середовища не потрібна; змінювати PowerShell ExecutionPolicy не потрібно.

На Linux/macOS: `python3.12 -m venv .venv`, далі `.venv/bin/python -m pip install -r requirements-dev.txt`.

## 2. BotFather та .env

1. В офіційному Telegram **@BotFather** виконайте `/newbot`, задайте ім'я та username.
2. Створіть конфігурацію, якщо її ще немає:

   ```powershell
   Copy-Item .env.example .env
   ```

3. Заповніть `BOT_TOKEN`, `DB_PASSWORD`, `ADMIN_IDS`, `IT_IDS`, `IT_GROUP_ID`. Приклад містить лише вигадані значення.
4. Для пароля БД використайте довгий випадковий рядок. Можна згенерувати локально: `python -c "import secrets; print(secrets.token_urlsafe(32))"`. Не надсилайте його в чат.
5. Не перезаписуйте наявну робочу `.env`. Вона виключена з Git і Docker build context. Токен не передавайте в URL браузера, командному рядку чи скриншотах; при витоку перевипустіть через BotFather.

| Змінна | Значення |
| --- | --- |
| BOT_TOKEN | Токен з BotFather |
| ADMIN_IDS | Додатні числові ID адміністраторів через кому; хоча б один |
| IT_IDS | ID спеціалістів через кому; адміністратори автоматично мають права ІТ |
| IT_GROUP_ID | Від'ємний chat_id закритої ІТ-групи, зазвичай починається з -100 |
| DB_PASSWORD | Пароль PostgreSQL |
| DB_HOST / DB_PORT / DB_USER / DB_NAME | Локальний Python; Compose задає db:5432, support, support |
| DATABASE_URL | Необов'язкова альтернатива для локального Python; має пріоритет над DB_* |

Compose передає пароль окремим параметром: символи `@`, `:`, `/` не ламають підключення. Значення `.env`, що містять `$` або `#`, беріть в одинарні лапки. У вручну заданому `DATABASE_URL` пароль потрібно URL-кодувати. Compose не передає локальний `DATABASE_URL` контейнеру.

## 3. Telegram ID і chat_id без сторонніх ID-ботів

1. Заповніть справжній `BOT_TOKEN` у `.env`; решта значень поки можуть залишатися прикладами.
2. Напишіть своєму боту `/id` у приватному чаті.
3. Створіть **закриту тестову ІТ-групу**, додайте бота й надішліть `/id@USERNAME_ВАШОГО_БОТА`. ІТ-спеціалісти також надсилають `/id` у приватному чаті.
4. Коли основний бот зупинений, виконайте:

   ```powershell
   .\.venv\Scripts\python.exe telegram_ids.py
   ```

   Скрипт звертається до Telegram з вашого комп'ютера й друкує лише числові ID для команд `/id`, без імен і текстів. Читає до 100 накопичених оновлень, не скидає їх; для нового бота цього достатньо.
5. Перенесіть ID у `.env`. Після запуску команда `/id` також працює у боті. При privacy mode у групі додавайте `@username`. Повідомлення анонімних адміністраторів/каналів не обробляються.

Усі учасники ІТ-групи бачать її повідомлення: не додавайте сторонніх. Членство в групі **не** дає прав керування заявками. Боту потрібні права надсилати повідомлення й фото; повні права адміністратора зазвичай не потрібні.

Після перетворення групи на супергрупу перевірте новий chat_id. Зміну робочої групи для наявної БД виконуйте окремою міграцією з повторною публікацією, а не просто заміною ID.

## 4. Docker Compose: запуск

Після заповнення `.env`:

```powershell
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 bot
```

`config --quiet` перевіряє конфігурацію без виводу секретів. Звичайний `docker compose config` може показати токен і пароль — не публікуйте його вивід.

Бот чекає healthcheck PostgreSQL (`service_healthy`). При старті у транзакції виконується `schema.sql` і реєструються ІТ/адміністратори. Схема створюється автоматично; адитивні зміни застосовуються також до наявного volume. Перед оновленням робочої БД зробіть резервну копію. Нові обмеження вводу діють для нових/змінених рядків; старі збережено без примусового очищення.

Порт БД не відкритий на хості. Дані зберігаються у `pgdata`. Контейнер бота працює непривілейованим користувачем з файловою системою лише для читання.

Healthcheck бота перевіряє БД і колонки схеми; **не доводить доступність Telegram чи справність polling**. Стан unhealthy сам по собі не перезапускає контейнер: restart спрацьовує при завершенні процесу.

```powershell
docker compose stop
docker compose up -d
```

Не використовуйте `docker compose down -v` для робочої БД: це видалить дані. Не запускайте локальний бот і контейнер одночасно з одним токеном.

## 5. Команди й перевірка першого запуску

| Роль | Команди / дії | Де |
| --- | --- | --- |
| Працівник | /start, /new, /my, /cancel | Приватний чат |
| Будь-хто | /id — тільки власний ID та ID поточного чату | Приватний чат / група |
| ІТ / адміністратор | /queue, /stats | Приватний чат або налаштована ІТ-група |
| ІТ / адміністратор | Взяти, очікування, продовжити, виконано, скасувати | Кнопки актуальної групової картки |
| Адміністратор | /pending, /pending TELEGRAM_ID, /approve TELEGRAM_ID, /reject TELEGRAM_ID | **Лише приватний чат** |
| Адміністратор | /sync | Приватний чат або ІТ-група |

`/pending` показує по 5 користувачів і команду наступної сторінки. Перевіряйте належність людини до підрозділу за внутрішнім каналом: введене ім'я не доводить особу.

`/reject` блокує користувача й скасовує непідтверджені заявки. Раніше опубліковані картки залишаються історією, але нові дії для заблокованого автора не виконуються. ІТ/адміністратора так заблокувати не можна: їхні права змінюють у списках ID середовища з перезапуском.

Перевіряйте на вигаданих даних у закритій тестовій групі:

1. Звичайний тестовий користувач: /start → /new → анкета. У /my — «Очікує перевірки»; у групі картки немає.
2. Адміністратор приватно: /pending → /approve ID. Попередня заявка з'являється в групі; наступна заявка цього користувача публікується відразу.
3. Два ІТ натискають «Взяти в роботу» — призначається один. Інший не може змінювати статус; адміністратор може.
4. Виконавець: очікування → продовжити → виконано. Перевірити картку, приватне сповіщення автора, /my, /queue, /stats.
5. Сторонній не може керувати кнопками й адміністративними командами. У чужій групі заявки й статистика не показуються.
6. Інший непідтверджений користувач: /reject ID — неперевірені заявки скасовані, доступ закрито.
7. Перезапуск: заявки лишаються; незавершена форма скидається. Після короткого збою мережі доставка відновлюється автоматично, також є /sync.

## 6. Автоматичні перевірки без Telegram

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m compileall -q bot.py config.py healthcheck.py telegram_ids.py tests
.\.venv\Scripts\python.exe -m pip check
```

Тести використовують вигадані ID, імена й токен, підміняють Telegram API. Імпорт bot.py не завантажує .env, не підключається до БД і не запускає polling.

Справжні SQL-запити, транзакції, повторна міграція та конкурентне призначення перевіряються окремо:

```powershell
docker compose -p support-bot-tests -f docker-compose.test.yml up --build --abort-on-container-exit --exit-code-from tests
docker compose -p support-bot-tests -f docker-compose.test.yml down
```

Тестовий Compose не використовує робочі секрети, порт чи volume. Його PostgreSQL має trust лише в окремій тестовій мережі без опублікованого порту, а дані тимчасові. Не застосовуйте trust до робочої БД.

Альтернатива: створіть окрему БД з назвою, що закінчується на `_test`, задайте `TEST_DATABASE_URL` у середовищі та виконайте pytest. Кожен інтеграційний тест створює випадкову схему й після завершення видаляє **тільки її**. Потрібні права створення схем. Без TEST_DATABASE_URL ці тести мають статус **SKIPPED**, а не успішний.

## 7. Локальний запуск без Docker

Потрібні Python 3.12+ і PostgreSQL. Створіть окрему роль support із паролем з .env та БД support з цією роллю як власником. Не використовуйте суперкористувача для бота.

Встановіть `requirements.txt` або `requirements-dev.txt`, задайте в .env: DB_HOST=localhost, DB_PORT=5432, DB_USER=support, DB_NAME=support, DB_PASSWORD.

Коли ви готові звертатися до Telegram зі справжнім токеном:

```powershell
.\.venv\Scripts\python.exe bot.py
```

Завершення — Ctrl+C. Шляхи до .env і schema.sql визначаються відносно файлу бота. У контейнері SIGTERM також закриває HTTP-сесію, FSM і пул БД; поточному оновленню дається до 25 секунд.

## 8. Типові помилки

| Симптом | Дії |
| --- | --- |
| docker не знайдено / daemon недоступний | Встановіть і запустіть Docker Desktop, перевірте WSL 2 та Linux containers. Unit-тести можна виконати без Docker. |
| Configuration / ValueError | Перевірте назву змінної у повідомленні, токен, додатні ID користувачів і від'ємний ID групи. Не залишайте REPLACE_*. |
| InvalidPasswordError | Пароль має відповідати наявній ролі PostgreSQL. Зміна DB_PASSWORD у .env не змінює пароль у вже створеному volume — оновіть роль через адміністратора БД. |
| ConnectionRefusedError / TimeoutError | Перевірте docker compose ps, healthcheck і DB_HOST. Усередині Compose хост — db, не localhost. |
| TelegramUnauthorizedError | Перевірте або перевипустіть токен через BotFather. |
| TelegramConflictError / немає відповідей | Зупиніть інший процес з тим самим токеном; перевірте webhook. |
| Webhook configured | Видаліть webhook через Telegram Bot API deleteWebhook з drop_pending_updates=False, використовуючи токен зі змінної середовища. |
| TelegramForbiddenError | Бота заблоковано або немає прав у групі. Перевірте членство, дозволи й IT_GROUP_ID; користувач має почати приватний діалог. |
| TelegramBadRequest під час доставки | Перевірте групу й наявність картки. Видалену вручну картку автоматично не відтворюємо, щоб не маскувати неправильну групу. |
| Фото не з'явилось | Приймається одне фото до 10 МБ, не альбом чи документ. Перевірте права на фото; повтори автоматичні. |
| /pending у групі мовчить | Виконуйте приватно від адміністратора — це захищає непідтверджених користувачів. |
| Дії тимчасово ігноруються | Ліміт — 10 дій за 10 секунд на користувача. Ліміт 3/20 заявок — за рухомі 24 години. |
| Тести SKIPPED | Не задано TEST_DATABASE_URL; запустіть тестовий Compose. |

## 9. Межі надійності й дані

- FSM у пам'яті: незавершена анкета після перезапуску втрачається. Заявки лишаються у PostgreSQL.
- Worker перевіряє доставку раз на 30 секунд; повтор однієї заявки — не раніше ніж через 60 секунд, до 50 заявок за цикл. Після довгого збою надсилається **актуальний** статус; усі переходи збережені в ticket_events.
- Telegram не має ключа ідемпотентності sendMessage: якщо він прийняв повідомлення, але відповідь загубилася чи процес упав до запису ID, повтор може створити дубль. Звичайні одночасні спроби серіалізовано; кнопки старого дубля не можуть змінити заявку.
- Якщо одержувач заблокував бота, поточне приватне сповіщення не повторюється безкінечно. Статус доступний у /my після відновлення доступу. Повідомлення про підтвердження/блокування облікового запису надсилаються один раз; статуси заявок мають повтори.
- Не надсилайте паролі, оперативні матеріали чи дані третіх осіб. Після підтвердження текст і фото бачать члени ІТ-групи. Непідтверджених користувачів переглядає адміністратор приватно.
- Логи містять тип помилки й назву операції, без токенів, SQL-параметрів, Telegram payload і traceback. Підтвердження/відхилення аудіюються в user_events, статуси — в ticket_events.
- Резервні копії, контроль доступу до хоста/volume, строки зберігання та перевірка відновлення налаштовуються адміністратором. Перед робочим використанням погодьте Telegram згідно з внутрішніми правилами.
- Перепризначення іншому ІТ, команда розблокування, Redis FSM, SLA, коментарі, експорт і вебпанель не реалізовані. Взяття в роботу й адміністративна зміна статусу збережені.
