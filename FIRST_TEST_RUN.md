## Що підготувати на комп'ютері

1. Встановіть Docker Desktop за [офіційною інструкцією Windows](https://docs.docker.com/desktop/setup/install/windows-install/), з WSL 2 і Linux containers. Якщо WSL потребує встановлення/оновлення або перезавантаження, виконайте кроки інсталятора.
2. Відкрийте Docker Desktop вручну та дочекайтеся запуску Engine. Перезапустіть термінал VS Code, щоб оновився PATH.
3. У терміналі виконайте:

   ```powershell
   docker info
   docker compose version
   ```

   `docker info` має повернути секцію Server без помилки підключення. Наявність лише версії CLI недостатня. Якщо Docker встановлений у нестандартному каталозі, повідомте шлях до `docker.exe`.

## Заповнення Telegram-конфігурації

Не перезаписуйте створену `.env` шаблоном. Пароль БД вже згенерований. Секрети вводьте лише локально, не надсилайте їх у чат.

1. Створіть **окремого тестового бота** через офіційний `@BotFather` → `/newbot`. Запишіть отриманий токен у `BOT_TOKEN`.
2. Створіть **окрему закриту тестову групу**, наприклад «Support Bot — тест». Не використовуйте робочу групу УПП. Додайте тестового бота й лише тестувальників, дозвольте боту надсилати повідомлення й фото.
3. Адміністратор і ІТ-тестувальник пишуть `/id` у приватному чаті тестового бота. У тестовій групі надішліть `/id@USERNAME_ТЕСТОВОГО_БОТА`. На цьому етапі відсутність відповіді нормальна: бот зупинений.
4. Для отримання ID є скрипт `telegram_ids.py`. Він **підключається до Telegram**, читає накопичені команди `/id` і показує лише ID. Запускайте його самостійно, коли готові до такого звернення; асистент до окремого дозволу його не запускатиме:

   ```powershell
   cd C:\Users\artur\Desktop\support_bot_vol\upp_support_bot
   ..\.venv312\Scripts\python.exe telegram_ids.py
   ```

   Це шлях до вже підготовленого Python 3.12 у цій робочій папці. Якщо створили власне середовище в папці проєкту, використовуйте `.\.venv\Scripts\python.exe`.
5. Перенесіть додатний Telegram ID адміністратора в `ADMIN_IDS`, ID ІТ-тестувальника — в `IT_IDS`, від'ємний `chat_id` **тестової групи** — в `IT_GROUP_ID`. Для кількох людей використовуйте кому.
6. Звичайного заявника й стороннього тестувальника **не додавайте** до `ADMIN_IDS` або `IT_IDS`. Для повної перевірки розмежування потрібні різні Telegram-акаунти: адміністратор, ІТ і звичайний користувач. Адміністратор автоматично має права ІТ.

## PostgreSQL-тести — не потребують Telegram

Коли Docker Engine запущений, із папки `upp_support_bot`:

```powershell
docker compose -p support-bot-tests -f docker-compose.test.yml up --build --abort-on-container-exit --exit-code-from tests
```

Це окремий проєкт із тестовою БД без робочих секретів і робочого volume. Критерій успіху: код виходу 0, усі 90 тестів проходять, **жодного skipped**. Якщо є помилки, спочатку виправляємо їх; бот ще не запускається.

Не застосовуйте `down -v`, `volume prune`, `system prune` і не видаляйте наявні томи. Цей документ не передбачає очищення даних.

## Перевірка конфігурації й дозвіл на запуск

Після заповнення всіх Telegram-змінних виконаємо:

```powershell
docker compose config --quiet
```

Не використовуйте звичайний `docker compose config`: він друкує розгорнуті секрети. Успішний `--quiet` перевіряє структуру, але не справжність токена й не те, що група тестова. Шаблонні ID також можуть пройти цю перевірку.

Перед першим запуском основного бота потрібно ваше явне підтвердження: **дозволяю підключити тестового бота; IT_GROUP_ID належить окремій тестовій групі**. До цього асистент не виконує `up` основного Compose й не звертається до Telegram.

Тільки після дозволу:

```powershell
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 bot
```

Перевіряємо стан контейнерів і healthcheck. Потім надішліть `/id` тестовому боту та перевірте відповідь. Повідомлення в логах «polling started» і healthcheck БД самі по собі не доводять, що бот успішно обробляє Telegram-оновлення. Остаточне підтвердження — відповідь бота та ручний сценарій нижче.

## Ручний контрольний список

Усі команди нижче — тестовому боту; адміністративні команди — **приватно**. Використовуйте вигадані дані, без фото справжнього обладнання або службових документів.

| Крок | Хто і що робить | Очікуваний результат |
| --- | --- | --- |
| 1 | Новий звичайний користувач: `/start` | Вітання та повідомлення, що користувач ще не підтверджений |
| 2 | Він же: `/new`; ім'я «Тестовий Працівник», підрозділ «Тестовий відділ», місце «Тестове місце», категорія «ПЗ», опис «Тестова несправність без службових даних», фото — «пропустити» | Бот видає номер заявки й статус «Очікує перевірки» |
| 3 | Заявник: `/my`; ІТ перевіряє тестову групу та `/queue` | Заявка є лише у власному списку автора; немає картки в групі й запису в ІТ-черзі, зокрема після циклу worker |
| 4 | Адміністратор: `/pending` | Видно тестового користувача й кількість його непідтверджених заявок |
| 5 | Адміністратор: `/approve ID_ЗАЯВНИКА` | Підтвердження успіху, у заявника — сповіщення |
| 6 | ІТ перевіряє тестову групу | З'являється картка **того самого номера** зі статусом «Нова»; при затримці доставки перевірити логи й `/sync` |
| 7 | ІТ-тестувальник: «Взяти в роботу» | Статус «В роботі», виконавець відповідає цьому ІТ, автор отримує сповіщення |
| 8 | Той самий ІТ: «Виконано» | Статус «Виконана», автор отримує сповіщення, активні кнопки зникають |
| 9 | Автор: `/my`; ІТ: `/stats` і `/queue` | У автора — «Виконана»; кількість виконаних зростає на 1 відносно початку тесту; активна черга не містить цю заявку |
| 10 | Звичайний користувач або інший сторонній тестовий акаунт: `/pending`, `/approve ID`, `/reject ID`, `/sync`, `/stats` | Немає адміністративних даних і змін. Мовчання допустиме: бот не обіцяє текстової відмови для цих команд. Адміністратор перевіряє, що користувачі/статуси не змінилися |

Для перевірки відсутності картки до схвалення зачекайте щонайменше один цикл worker (приблизно 30 секунд за відсутності затримок). Не додавайте сторонніх у реальну робочу групу навіть заради перевірки прав.

Після сценарію повідомте лише номери тестових кроків і результат. Токен, пароль, реальні тексти заявок та службові скриншоти не потрібні.
