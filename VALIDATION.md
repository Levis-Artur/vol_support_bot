# Результати перевірок

## Відкритий прийом заявок — поточні локальні зміни

Прибрано залежність від `users.verified`, команди `/pending` і `/approve`. Нові заявки мають статус `new`; ліміт для всіх — 5 за рухомі 24 години. Додано `/block` і `/unblock` з аудитом, повторно виконувану міграцію старих заявок і поступову доставку. Виправлено умову middleware, яка відкидала дії в групі. Процедура резервного копіювання перед міграцією — у MIGRATION_OPEN_ACCESS.md.

До останньої вказівки власника припинити написання й запуск тестів локально виконано pytest: **89 passed, 16 skipped**. Пропущено PostgreSQL-інтеграційні тести через відсутність тестової БД. Ruff пройшов на попередньому проміжному стані; після останніх змін повторно не запускався. Після вказівки власника нові тести не додаються й перевірки не запускаються.

Ця версія ще не перевірена на справжньому PostgreSQL, Docker або Telegram. Робоча БД і Docker volumes не змінювалися, міграція на сервері не виконувалася, `.env` не змінювався. Раніше успішний CI нижче стосується попередньої версії й не підтверджує нові зміни.

## Попередня локальна перевірка — 14 жовтня 2026 року

Початкові зміни зроблено без запуску polling, без реального токена й без звернень до Telegram. На тому етапі `.env` не створювали й не читали. Переглянуто всі початкові файли, включно з технічним ТЗ та прихованими прикладами конфігурації.

## Повторна підготовка першого запуску

`docker info` і `docker compose version` не змогли виконатися: Docker CLI відсутній у PATH. Docker Desktop не знайдено також у стандартних системному та користувацькому каталогах. Engine і контейнери не перевірено.

На цьому етапі створено `.env` із шаблону та згенеровано випадковий пароль БД без його виводу. BOT_TOKEN, ADMIN_IDS, IT_IDS, IT_GROUP_ID залишилися шаблонними; запуск бота заблоковано. Правила виключення `.env` із Git і двох Docker build context перевірено. Git-репозиторій у папці не ініціалізований, тому стан Git index не перевірявся.

Compose-файли не потребують портів хоста: `ports` і host networking відсутні. Перевірка TCP через .NET також показала відсутність слухачів порту 5432 на хості. Повторного запуску pytest не було: наведені нижче 83 passed / 7 skipped — попередній результат. PostgreSQL-інтеграція й Telegram досі не перевірені. Код не змінювали, дані й томи не видаляли.

Точні наступні дії та ручний контрольний список: [FIRST_TEST_RUN.md](FIRST_TEST_RUN.md). Після встановлення Docker необхідно виконати всі 90 тестів без пропусків. Перед підключенням бота потрібно явне підтвердження користувача та підтвердження використання окремої тестової групи.

## Виконано

- Python 3.12 у локальному ізольованому середовищі; aiogram 3.31.0, asyncpg 0.32.0.
- `python -m pytest -q`: **83 passed, 7 skipped**.
- `python -m ruff check .`: **All checks passed**.
- `python -m compileall -q bot.py config.py healthcheck.py telegram_ids.py tests`: успішно.
- `python -m pip check`: **No broken requirements found**.
- Перевірено граматику `schema.sql`, PL/pgSQL-міграції та всіх SQL-літералів запитів через PostgreSQL-парсер pglast.
- YAML Compose прочитано й перевірено статично: БД без опублікованого порту, обов'язкові змінні, healthcheck і `service_healthy`. Це не замінює `docker compose config` чи запуск контейнерів.

Автоматизовані сценарії: анкета FSM через справжній Dispatcher aiogram, повторне надсилання, ліміти 3/20, підтвердження й відхилення, права ІТ/адміністратора, блокування, власні заявки, усі основні переходи статусів, застарілі callback, пагінація, статистика, HTML, захист логів, відмова Telegram, завершення поточного обробника.

## Не виконано через середовище

Docker CLI/daemon і PostgreSQL тут недоступні. **7 інтеграційних тестів пропущено**: виконання міграцій і SQL на сервері, конкурентне призначення та публікація, ліміти й дублювання на БД, відхилення та CHECK, відновлення доставки, SQL статистики/черги. Вони готові в `tests/test_postgres.py` й запускаються окремим `docker-compose.test.yml` без робочих секретів.

Docker build, виконання healthcheck, справжня доставка Telegram, права бота у групі та запуск polling не перевірялися. Перед прийманням тестового розгортання виконайте Docker-тести й ручний сценарій з README.

## Відомі обмеження

Незавершена FSM-форма не переживає перезапуск. Після невизначеного результату `sendMessage` можливий дубль повідомлення: Telegram не надає ключа ідемпотентності. Повтори статусів доставляють актуальний стан; історія переходів зберігається в БД. Видалені вручну картки автоматично не відтворюються. Healthcheck перевіряє БД, але не Telegram.

За доступними перевірками критичних помилок не виявлено. Повна перевірка готовності потребує проходження PostgreSQL/Docker-тестів і першого тестового Telegram-сценарію.
